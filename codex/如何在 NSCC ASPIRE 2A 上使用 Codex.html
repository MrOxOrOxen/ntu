如何在 NSCC ASPIRE 2A 上使用 Codex（SSH 隧道、CLI、VS Code 与排障）

用途：帮助 NSCC ASPIRE 2A 用户从零配置 Codex CLI；也可把本页完整发送给 AI agent，由 agent 在用户监督下完成配置。

最后实测：2026-08-29（macOS → NSCC NTU login node；Codex CLI v0.150.1）。

合规与边界：先确认所在实验室、机构和 NSCC 允许这种仅绑定回环地址的 SSH 反向转发。所有训练、推理、GPU、长时间脚本及其他计算任务必须通过 NSCC 调度器运行；login node 只用于编辑、轻量检查、提交任务和 Codex 交互。当前代理入口只存在于建立 SSH 的那台 login node，进入 compute node 后，127.0.0.1 指向另一台机器，不能继续使用本页的代理端口。

1. 原理与成功标准

Codex 在 NSCC 上访问 OpenAI 时，网络路径如下：

flowchart LR
  A["Codex CLI<br>NSCC login node"] --> B["HTTP proxy<br>127.0.0.1:REMOTE_PORT<br>NSCC"]
  B -->|"SSH RemoteForward"| C["HTTP proxy<br>127.0.0.1:LOCAL_PORT<br>用户电脑"]
  C --> D["OpenAI"]

这里有两个不同机器上的 127.0.0.1：

  • 127.0.0.1:LOCAL_PORT 位于用户电脑，例如 8899。
  • 127.0.0.1:REMOTE_PORT 位于当前 NSCC login node，例如 17891。
  • SSH 配置中的 RemoteForward 把 NSCC 的远端端口映射回用户电脑的本地代理。

完整成功标准：

  • 用户电脑的代理只监听 127.0.0.1:LOCAL_PORT。
  • 用户电脑经该代理访问 OpenAI API 得到 HTTP_401，而不是超时或拒绝连接。
  • ssh nscc 能正常进入 NSCC，且不会出现 remote port forwarding failed。
  • NSCC 上经 127.0.0.1:REMOTE_PORT 测试同样得到 HTTP_401。
  • 在项目目录运行 codex 后能够得到实际回复。
HTTP_401 在本文的无凭据 curl 测试中表示网络路径已经到达需要认证的 HTTP 服务；它不是 Codex 登录成功的证明。最终仍须让 Codex 实际回复一次。

2. 配置前填写信息

先记录以下值，后文所有占位符都必须替换：

NSCC_USER=<你的 NSCC 用户名>
NSCC_HOST=<所属机构的 NSCC SSH 入口>
SSH_ALIAS=nscc
LOCAL_PORT=8899
REMOTE_PORT=17891
LOCAL_OS=<macOS / Linux / WSL2>

NTU 用户常用入口是 aspire2antu.nscc.sg；其他机构用户应以 NSCC 提供的信息为准。端口只作为示例：本地端口和远端端口可以不同，但全文必须保持一致。

3. 强制备份规则

任何脚本或 AI agent 修改文件前，必须先备份将要修改的确切文件。不要把密码、token、私钥或 ~/.codex/auth.json 复制到共享备份目录。

3.1 用户电脑

backup_dir="$HOME/nscc-codex-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
chmod 700 "$backup_dir"

test -f "$HOME/.ssh/config" && cp -p "$HOME/.ssh/config" "$backup_dir/ssh-config.before"

printf 'Backup: %s\n' "$backup_dir"

3.2 NSCC

登录 NSCC 后另建远端备份：

backup_dir="$HOME/nscc-codex-backup-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
chmod 700 "$backup_dir"

test -f "$HOME/.bashrc" && cp -p "$HOME/.bashrc" "$backup_dir/bashrc.before"
test -f "$HOME/.vscode-server/server-env-setup" && \
  cp -p "$HOME/.vscode-server/server-env-setup" "$backup_dir/vscode-server-env.before"

printf 'Backup: %s\n' "$backup_dir"

记录两个备份目录。修改出错时，从相应的 .before 文件恢复。不要删除原文件后重建；优先覆盖恢复并保留权限。

4. 在用户电脑启动本地 HTTP 代理

以下用 Python 的 proxy.py 作为简单实现。若实验室已有经过批准的本地 HTTP 代理，可直接使用，并把 LOCAL_PORT 改成实际端口。

4.1 macOS / Linux / WSL2 首次安装

python3 -m venv "$HOME/.local/share/nscc-codex-proxy"
"$HOME/.local/share/nscc-codex-proxy/bin/pip" install --upgrade pip proxy.py

4.2 每次开机后启动

在一个专用本地终端运行，并在使用期间保持该终端、电脑和网络在线：

"$HOME/.local/share/nscc-codex-proxy/bin/proxy" \
  --hostname 127.0.0.1 \
  --port 8899 \
  --num-workers 1 \
  --num-acceptors 1

不要把 --hostname 改成 0.0.0.0。

4.3 本地验证

macOS：

lsof -nP -iTCP:8899 -sTCP:LISTEN

Linux / WSL2：

ss -ltn | grep 8899

然后在用户电脑执行：

curl -sS -o /dev/null -w 'HTTP_%{http_code}\n' \
  --connect-timeout 10 \
  --max-time 20 \
  --proxy http://127.0.0.1:8899 \
  https://api.openai.com/v1/models

预期为 HTTP_401。若出现 HTTP_000、connection refused 或超时，先修复本地代理，不要继续配置 SSH。

5. 配置 SSH 反向转发

本文默认使用操作系统自带终端和系统 OpenSSH。开始前运行 type ssh；它应指向系统 ssh 可执行文件，而不是 shell function 或第三方 wrapper。若被改写，请先在默认终端中新开一个干净 shell 再继续。

5.1 创建稳定的控制 socket 目录

mkdir -p "$HOME/.ssh/sockets"
chmod 700 "$HOME/.ssh" "$HOME/.ssh/sockets"
touch "$HOME/.ssh/config"
chmod 600 "$HOME/.ssh/config"

5.2 编辑 ~/.ssh/config

如果已经存在 Host nscc，修改原有段落，不要重复创建同名段落。示例：

Host nscc
  HostName <NSCC_HOST>
  User <NSCC_USER>
  ServerAliveInterval 60
  ServerAliveCountMax 3
  ExitOnForwardFailure yes
  RemoteForward 127.0.0.1:17891 127.0.0.1:8899
  ControlMaster auto
  ControlPath ~/.ssh/sockets/%C
  ControlPersist 600

如果账号只能使用密码认证，可按实际情况添加：

PreferredAuthentications keyboard-interactive,password
PubkeyAuthentication no

不要为其他使用者默认禁用公钥认证；先遵循其 NSCC 账号的实际认证方式。

5.3 检查有效配置

ssh -G nscc | grep -Ei \
  '^(hostname|user|remoteforward|controlmaster|controlpath|controlpersist|exitonforwardfailure) '

确认主机、用户名、17891 → 8899 映射和稳定的 ~/.ssh/sockets/... 控制路径均正确。

5.4 首次连接

正常使用只需：

ssh nscc

这条命令会同时建立交互 shell、SSH master 和反向转发。除非只想建立后台隧道，否则不需要先运行 ssh -MNf nscc。

连接成功后，可在另一个本地终端检查：

ssh -O check nscc

预期显示 Master running。

6. 在 NSCC 设置代理环境

登录 NSCC 后，先确认当前节点：

hostname -s
printf 'PBS_JOBID=%s\n' "$PBS_JOBID"

在完成远端备份后，把下面代码合并到 ~/.bashrc。若文件含有“非交互 shell 直接 return”的逻辑，应把这段放在它之前：

# >>> nscc-codex-proxy >>>
case "$(hostname -s)" in
  asp2a-login-*)
    export HTTP_PROXY="http://127.0.0.1:17891"
    export HTTPS_PROXY="$HTTP_PROXY"
    export http_proxy="$HTTP_PROXY"
    export https_proxy="$HTTPS_PROXY"
    export NO_PROXY="localhost,127.0.0.1,::1"
    export no_proxy="$NO_PROXY"
    export PATH="$HOME/.local/bin:$PATH"
    ;;
esac
# <<< nscc-codex-proxy <<<

重新登录，或在当前 shell 执行：

source "$HOME/.bashrc"
printf 'HTTPS_PROXY=%s\n' "$HTTPS_PROXY"

预期为 http://127.0.0.1:17891。

6.1 从 NSCC 验证完整隧道

ss -ltn | grep 17891

curl -sS -o /dev/null -w 'HTTP_%{http_code}\n' \
  --connect-timeout 10 \
  --max-time 20 \
  --proxy http://127.0.0.1:17891 \
  https://api.openai.com/v1/models

预期远端 127.0.0.1:17891 正在监听，且 curl 返回 HTTP_401。

7. 安装、登录和验证 Codex CLI

OpenAI 官方当前提供的 macOS/Linux 安装方式是：

curl -fsSL https://chatgpt.com/codex/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"

验证安装：

command -v codex
codex --version

进入需要处理的项目目录再启动：

cd "$HOME/<项目目录>"
codex

首次运行时按屏幕提示选择 “Sign in with ChatGPT” 或其他可用登录方式。密码、登录代码、token 和 ~/.codex/auth.json 只能由用户本人处理，不得发送给 AI agent、聊天或文档。

进入 Codex 后可执行：

/status

然后发送一个最小测试：

请只回复：READY

收到 READY 才代表代理、SSH 隧道、Codex 登录和 API 调用全部成功。

8. 可选：VS Code Remote-SSH

如果只使用 Codex CLI，可跳过本节。

  1. 本地 VS Code 安装 “Remote - SSH”。
  1. 使用 Remote-SSH: Connect to Host...，选择 nscc alias。
  1. 在远端窗口打开 NSCC 工作目录。
  1. 确认 Codex 扩展安装在 SSH 远端环境，而不是只安装在本地 UI。

若 VS Code Server 没有继承 ~/.bashrc 中的代理变量，可在备份后合并以下文件：

~/.vscode-server/server-env-setup

内容示例：

#!/bin/sh
case "$(hostname -s)" in
  asp2a-login-*)
    export HTTP_PROXY="http://127.0.0.1:17891"
    export HTTPS_PROXY="$HTTP_PROXY"
    export http_proxy="$HTTP_PROXY"
    export https_proxy="$HTTPS_PROXY"
    export NO_PROXY="localhost,127.0.0.1,::1"
    export no_proxy="$NO_PROXY"
    export PATH="$HOME/.local/bin:$PATH"
    ;;
esac

然后验证语法并重新启动远端 VS Code Server：

chmod 600 "$HOME/.vscode-server/server-env-setup"
sh -n "$HOME/.vscode-server/server-env-setup"

sh -n 没有输出表示语法检查通过。保存工作后，使用 “Remote-SSH: Kill VS Code Server on Host...” 再重新连接。

9. 每次开机后的日常流程

  1. 启动用户电脑上的本地代理。
  1. 用 lsof 或 ss 确认 127.0.0.1:8899 正在监听。
  1. 执行本地 curl，确认得到 HTTP_401。
  1. 运行 ssh nscc；这一步自动建立/复用 SSH master 和远端 17891 转发。
  1. 在 NSCC 执行远端 curl，确认得到 HTTP_401。
  1. 进入项目目录运行 codex。
  1. 使用期间保持用户电脑开机、网络在线、本地代理进程存活。

第二个终端直接再次运行：

ssh nscc

它应复用当前 master。结束全部远端会话后，可在用户电脑执行：

ssh -O exit nscc

最后回到代理终端按 Ctrl-C 停止本地代理。

10. 故障诊断

10.1 remote port forwarding failed for listen port 17891

含义：NSCC 当前 login node 上的 127.0.0.1:17891 已被占用，或服务端拒绝了反向转发。由于配置包含 ExitOnForwardFailure yes，SSH 会退出，这是预期的保护行为。

先检查本机 master：

ssh -O check nscc
  • 若显示 Master running：不要建立第二条隧道，直接 ssh nscc。
  • 若控制 socket 不存在：使用下面的诊断连接进入 NSCC；它只用于排查，不建立新转发。
ssh -o ClearAllForwardings=yes \
  -o ControlMaster=no \
  -o ControlPath=none \
  nscc

在 NSCC 检查：

ss -ltn | grep 17891
curl -sS -o /dev/null -w 'HTTP_%{http_code}\n' \
  --connect-timeout 10 --max-time 20 \
  --proxy http://127.0.0.1:17891 \
  https://api.openai.com/v1/models
  • 监听存在且得到 HTTP_401：已有隧道可用；查找它对应的本机 SSH 进程，不要盲目换端口。
  • 监听存在但请求失败：可能是失效的旧隧道；先在本机逐一确认相关 SSH 进程及其网络连接，再仅终止确定的遗留进程。禁止使用 pkill ssh 或 killall ssh。
  • 没有监听：更可能是 NSCC 服务端策略或绑定失败。停止反复尝试，联系 NSCC support。

10.2 Control socket connect(...): No such file or directory

含义：当前没有可管理的 SSH master，或临时 socket 已被删除。

  • 若路径位于 ~/.ssh/sockets/...：直接运行 ssh nscc 创建新 master。
  • 若路径位于意外的 /tmp/...：检查 type ssh 和实际启动参数，确认是否有第三方 wrapper；改用默认终端和系统 OpenSSH 后再试。

10.3 本地端口监听正常，但本地 curl 失败

代理进程存在不代表它能访问互联网。使用：

curl -sv --proxy http://127.0.0.1:8899 \
  https://api.openai.com/v1/models \
  -o /dev/null

检查 HTTPS CONNECT 是否成功。若失败，处理用户电脑的网络、VPN、防火墙或代理实现。

10.4 NSCC curl 得到 HTTP_401，Codex 仍不能回复

依次确认：

  1. printf '%s\n' "$HTTPS_PROXY" 指向 127.0.0.1:17891。
  1. Codex 是在设置代理变量之后启动的；否则退出并重新运行。
  1. 按 Codex 登录提示重新登录。
  1. 不要把 curl 的 401 当作 Codex 认证成功；用实际 Codex 回复作为最终验证。

10.5 WARNING: failed to clean up stale arg0 temp dirs

如果 Codex 随后正常进入界面并能够回复，这是非致命的临时目录清理警告。不要因此递归删除 /tmp、~/.codex 或共享目录。只有在它实际阻止 Codex 启动时，才检查警告指出的具体目录、所属用户和正在运行的 Codex 进程。

10.6 Post-quantum key exchange 警告

connection is not using a post-quantum key exchange algorithm 是服务器算法能力提示，与远端端口转发失败无关。普通用户无法通过改端口解决；是否升级由 NSCC 管理员决定。

10.7 进入 compute node 后代理失效

这是网络作用域导致的正常现象。SSH 的 127.0.0.1:17891 只监听当前 login node。不要将它改成 0.0.0.0 或开启 GatewayPorts。计算任务通过调度器提交；如确实需要 compute node 出网，应先向 NSCC support 申请批准的方案。

11. 回滚

回滚前先停止相关 Codex 和 SSH 会话。使用第 3 节记录的准确备份路径，例如：

cp -p "$LOCAL_BACKUP/ssh-config.before" "$HOME/.ssh/config"

NSCC：

cp -p "$REMOTE_BACKUP/bashrc.before" "$HOME/.bashrc"
test -f "$REMOTE_BACKUP/vscode-server-env.before" && \
  cp -p "$REMOTE_BACKUP/vscode-server-env.before" "$HOME/.vscode-server/server-env-setup"

其中 LOCAL_BACKUP 和 REMOTE_BACKUP 必须替换为第 3 节实际输出的目录。恢复后新开终端，并用 ssh -G nscc、sh -n 和逐层 curl 重新验证。

12. 可直接发送给 AI agent 的执行协议

把本页链接和下面提示一起发送给 agent，并先填写变量：

请按照所附《在 NSCC ASPIRE 2A 上使用 Codex》文档协助我配置。

我的信息：
NSCC_USER=<填写>
NSCC_HOST=<填写>
SSH_ALIAS=nscc
LOCAL_PORT=8899
REMOTE_PORT=17891
LOCAL_OS=<macOS/Linux/WSL2>

执行约束：
1. 先做只读检查：操作系统、shell、type ssh、代理监听、~/.ssh/config、ssh -G nscc、现有 SSH 进程和控制 socket。
2. 修改任何文件前，创建时间戳备份，列出备份路径、文件、权限和校验值；禁止备份或展示密码、私钥、token、登录代码、~/.codex/auth.json。
3. 每次只做一个最小修改；修改后立即验证。保留用户无关配置，不覆盖整个 dotfile。
4. 不得要求或读取我的 NSCC 密码。需要密码时暂停，让我在 SSH 提示中亲自输入。
5. 禁止 rm -rf、pkill ssh、killall ssh、批量删除 socket、扫描大量端口、绑定 0.0.0.0、开启 GatewayPorts。
6. 结束 SSH 进程前，必须展示 PID、完整命令、启动时间、TTY 和 lsof 网络连接，并确认它是孤立的 NSCC 隧道。
7. 确认使用系统 OpenSSH；如果 type ssh 显示 function 或第三方 wrapper，先切换到默认终端的干净 shell。
8. 按“本地代理 → SSH RemoteForward → NSCC curl → Codex 实际回复”逐层验证，不得跳步。
9. 若远端转发连续两次被服务端拒绝且不存在端口占用，停止修改并建议联系 NSCC support。
10. 最终报告：修改了什么、未修改什么、验证结果、备份路径、回滚命令、仍存在的风险。

AI agent 不应接触 NSCC 密码、ChatGPT 登录代码、API key、私钥或 Codex 认证文件。涉及密码和网页登录的步骤必须交还给用户本人完成。

13. 最终验收清单

  • 本地代理只监听 127.0.0.1:8899。
  • 本地代理测试得到 HTTP_401。
  • type ssh 指向系统 OpenSSH，而不是 shell function 或第三方 wrapper。
  • ssh -G nscc 显示正确主机、用户、端口和稳定 ControlPath。
  • ssh nscc 能直接登录，无远端端口冲突。
  • ssh -O check nscc 显示 master 正常。
  • NSCC 127.0.0.1:17891 正在监听。
  • NSCC 代理测试得到 HTTP_401。
  • codex --version 正常。
  • Codex 能在项目目录实际回复 READY。
  • 所有重型计算仍通过 NSCC 调度器运行。
  • 用户已记录备份与回滚路径。
